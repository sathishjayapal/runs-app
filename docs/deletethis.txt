# Database Access Modernization & PCI Scope Optimization
**Sanitized Enterprise Architecture proposal | Working draft | Not approved for production or PCI reclassification**

> **Executive takeaway:** Establish separate standards for privileged human database access and protected application data consumption. Measure security effectiveness first; assess any PCI scope change independently with authorized Compliance/QSA review.

### Slide 1 — Two distinct access needs call for two complementary enterprise standards
**Message:** Privileged administrators and applications require different controls. A universal access intermediary may add complexity without delivering equivalent value.
**Visual:** Two lanes: privileged human access and protected application access.
**Decision:** Endorse separate standards for evaluation.

### Slide 2 — Privileged database access should be assessed for control effectiveness, not automatic descoping
**Message:** Existing PAM capabilities should be the baseline; database-aware brokerage is an optional incremental control.
**Visual:** Human → IAM/MFA/JIT/PAM → [optional database broker] → segmentation → database.
**Evidence:** Attribution, least privilege, session logging, bypass testing, emergency access, engine compatibility.
**Decision:** Approve a limited DBA pilot.

### Slide 3 — Protected data services offer a strategic way to minimize unnecessary PAN exposure
**Message:** Applications should prefer constrained business operations that return the minimum authorized data.
**Visual:** App → API authn/authz → protected service → CDE source / tokenization control.
**Evidence:** Data flow, response validation, token reversibility, alternate access paths, logs, cache and exports.
**Decision:** Authorize application-pattern discovery.

### Slide 4 — Reuse existing controls before purchasing a new enterprise intermediary
**Message:** Score technologies against mandatory controls, compatibility and incremental TCO; do not treat vendor marketing as proof.
**Visual:** Vendor-fit matrix, with unverified cells explicitly marked.
**Decision:** Agree evaluation gates.

### Slide 5 — PCI scope transitions must follow evidence, not infrastructure placement
**Message:** Segmentation, intermediaries, SNAT or TLS termination alone do not establish out-of-scope status.
**Visual:** Scope decision funnel: data handling → connectivity/security impact → effective isolation → testing → review.
**Decision:** Agree QSA/compliance review criteria.

### Slide 6 — A 90-day assessment can deliver an architecture decision without premature deployment commitments
**Message:** Baseline → pilot → standardize.
**Deliverables:** Persona matrix, test report, TCO comparison, draft ADD, unresolved-risk register.
**Decision:** Authorize discovery and validation; no vendor award or category change.

## Reference architecture A — Privileged human database access

```mermaid
flowchart TD
    A["Authorized DBA / support user"] --> B["Corporate identity, MFA, approval and JIT"]
    B --> C["Approved privileged access platform"]
    C --> D{"Does a DB-aware broker add validated value?"}
    D -->|Yes| E["Optional database access broker"]
    D -->|No| F["Approved segmentation controls"]
    E --> F
    F --> G["Protected database"]
    C -.-> H["Centralized audit and monitoring"]
    E -.-> H
    G -.-> H
```

**Control requirements:** named accountability; time-bounded permissions; least privilege; no unmanaged bypass; database-native authorization; attributable audit; break-glass procedures; resilience; database/driver/version compatibility.

**PCI position:** privileged users, management components and workstations may remain in scope where they connect to or can affect CDE security. Do not assign an out-of-scope classification from broker placement alone.

## Reference architecture B — Protected application data access

```mermaid
flowchart TD
    A["Business app or batch consumer"] --> B["Approved API / service authentication and authorization"]
    B --> C["Protected data service: allowlisted operations"]
    C --> D["CDE data source"]
    C --> E["Approved tokenization / data protection"]
    C --> F["Response minimization and validation"]
    F --> A
    C -.-> G["Security telemetry / evidence"]
    E -.-> G
```

**Control requirements:** no general-purpose SQL exposure; least-privileged service identity; field-level minimization; token properties tested; detokenization controlled; logs, error messages, backups and caches checked; failure behavior and bypass paths tested.

**PCI position:** a protected service and associated tokenization/key controls may remain in scope. A downstream consumer is only a potential out-of-scope candidate after its effective relationships and data handling are assessed.

## Vendor fit — candidate categories, not approved product findings

| Capability | Example candidates | Initial evaluation question | Status |
|---|---|---|---|
| PAM and privileged sessions | CyberArk or approved PAM | Which deployed modules meet MFA/JIT/session requirements? | To validate internally |
| Database-aware brokering | StrongDM or equivalent | Which exact protocols, database versions and SQL controls are supported? | To validate with vendor and pilot |
| Tokenization | OpenText Voltage, Protegrity or equivalent | What are token properties, key custody and detokenization boundaries? | To validate |
| API controls | Approved API gateway | Can business operations and response fields be constrained? | To validate |
| Database activity monitoring | Approved DAM platform | Does it provide usable, attributable and tamper-resistant evidence? | To validate |
| Network segmentation | Approved firewall/network controls | Is bypass resistance demonstrated by tests? | To validate |

**Compatibility caution:** Never infer Db2 for z/OS compatibility from a claim about Db2 LUW or IBM i. Do not assume an HTTPS inspection control can inspect native SQL protocols.

## Cost and value method

Three-year incremental TCO = one-time implementation + 3 × (annual licensing + annual infrastructure + annual operations + annual assurance).

The companion workbook contains **hypothetical editable assumptions**, not vendor quotes, bank spending, or approved savings. Compare baseline PAM with PAM-plus-broker and document *incremental* controls achieved.

**Benefits to measure:** standing privileges, unmanaged paths, access-provisioning time, individual session attribution, audit evidence preparation time, and successful policy-enforcement tests. Do not monetize PCI scope reduction without approved evidence and cost confirmation.

## QSA and governance gates

1. Verify CHD data flows and where PAN is stored, processed or transmitted.
2. Assess whether systems connect to or can impact CDE security.
3. Test segmentation and alternative paths, including emergency/maintenance conditions.
4. Validate access rights, administrative reach and control-plane dependencies.
5. Test token reversibility and unauthorized detokenization.
6. Inspect logs, exports, errors, caches and backups for unintended CHD exposure.
7. Validate fail-safe behavior, monitoring, resilience and identity attribution.
8. Obtain documented internal security/compliance review and QSA assessment as applicable.
9. Record final classification in the bank's authorized inventory and governance process.

**Classification note:** Internal Cat1/Cat2/Cat3 terminology must be mapped to actual PCI DSS scoping criteria; Cat2 connected/security-impacting components remain in scope. QSA assessment is not a substitute for management ownership and approval.

## Pilot acceptance criteria

| Test | Pass condition |
|---|---|
| Privileged identity | Each privileged action attributable to an authorized identity |
| Time-bounded access | Access expires and is revoked as designed |
| Bypass | Unauthorized direct database paths denied |
| SQL/role restrictions | Forbidden operations denied by effective controls |
| Break-glass | Approved emergency path works and is reviewable |
| Engine compatibility | Representative driver/version/operations tested |
| Evidence | Relevant logs are complete, protected and correlatable |
| Failure mode | Defined behavior under broker/PAM outage demonstrated |
| Performance | Latency and availability satisfy approved objectives |
| Compliance | No reclassification claimed without formal assessment |

## Proposed 90-day plan
**Days 0–30:** baseline personas, inventory controls, select pilot use cases, collect entitlement and compatibility facts.  
**Days 31–60:** compare PAM-only and broker-assisted controls, run negative/bypass/failure tests, collect actual implementation effort.  
**Days 61–90:** publish ADD, cost comparison, reference patterns, evidence package and decision log.

## Decision requested
Approve a limited architecture evaluation of the two standards and their validation criteria. Do **not** approve a new enterprise product, production deployment or PCI classification transition based on this proposal alone.
